# 智慧学伴 · 三人团队 DSH 协作开发方案

> 依据：1_赛题规则.pdf（9页）、2_参赛说明.docx、3_典型案例说明.docx、赛题数据说明.docx、模拟学情数据（实测统计）
> 赛题：第二届北京市大学生"人工智能+"创新大赛 · "智慧学伴"——学情诊断与个性化学习智能体构建（北京数据集团）

## 0. 一句话结论

DSH 不是参赛作品，而是三人的**第二个工程师 + 文档工厂**：把"读资料、跑数据、写代码、出文档"这批重活流水线化；团队只保留两件 DSH 替代不了的事——**教学语义判断**和**结果背书**。
组织形式：**三条泳道并行 + 一份数据契约收口 + 一个红队复核**。

## 1. 先分清两层（这决定怎么分工）

| 层 | 内容 | 谁负责 | 评分地位 |
|---|---|---|---|
| 层 A：交付物 | "智慧学伴"智能体本体：输入课标/教材/题目/作答 → 输出任务1内容图谱、任务2学情诊断、任务3个性化建议，全部可机读 | 三人共同 | 全部 16 个评分项都只看这一层 |
| 层 B：研发流水线 | DSH 工作区：读写文件、跑 Python/pandas、生成 docx/xlsx/pptx/pdf 并渲染校验、子智能体并行、项目记忆、定时检查点 | 工程官主导，另两人日常使用 | 不直接得分，但决定"三周能不能做完 + 能不能复现" |

评委不会问"你们用了什么工具"，但会问"这个结论的依据在哪、换一批学生还能不能跑"。所以层 B 的产物要能一键重跑，层 A 的每个数字要能点回原始记录。

## 2. 交付物清单（对齐规则第 3 节 16 个评分项）

| 交付物 | 硬约束 | 主要对应评分维度 |
|---|---|---|
| 设计方案文档 PDF | ≤20 页，含需求分析/方案设计/功能说明/结果验证/创新点，须写明任务使用平台、完成方式、数据使用范围、关键结果依据 | 文档与演示质量 |
| 任务成果包 | JSON/CSV 等可机读结果 + 字段说明 + 输入输出样例 + 操作说明 | 三项任务质量 + 复核材料充分 |
| 演示视频 MP4 | ≤5 分钟，展示三项核心任务完成过程 + 典型案例分析结果/建议/依据查看方式 | 演示完整、时长合规 |
| 现场答辩 PPT | 10 分钟讲解 + 5 分钟问答（材料评审 80%，答辩 20%） | 全部维度 |
| 分析脚本/代码 | **可选**；但不论交不交，都必须给"足以核对关键结果的输入样例 + 输出 + 说明" | 复核材料充分 |

注意"代码可选"是个陷阱：不交代码就必须把输入样例、输出、字段说明做到能被人手工核对的程度，工作量并不更小。建议直接交代码 + 一键复现脚本。

## 3. 三人分工：按"责任田"，不按技术栈

| 角色 | 主责 | 关键产出 | 在 DSH 里的主要用法 |
|---|---|---|---|
| A 内容官（课程/教材/题目） | 任务 1：三个主题（T01 代数式与整式运算 / T02 方程与方程组 / T03 不等式与不等式组）的学习内容与要求梳理，标到课标页、教材页、题目 | content_map.json + 内容图谱表（主题→指标→课标 CR 编号/页码→教材页→题目） | 让 DSH 批量解析 5_课程标准及相关教学资源 的 PDF 切片，抽取"课标条目—教材页码—题目"三元组，生成待人工确认清单 |
| B 数据官（质检/指标/诊断） | 任务 2：806 条作答记录的清洗、口径、个体+群体诊断 | quality_report.md（异常清单）+ diagnosis.json + 统计表 | DSH 跑 pandas 质检脚本、生成指标、把每个结论反查到记录编号 |
| C 工程与表达官（智能体/材料/答辩） | 智能体编排与封装、schema、演示视频、PDF/PPT、答辩 | 可运行 agent + 三份 schema + 四件套材料 | DSH 生成 docx/pptx/pdf 并渲染校验版式；用子智能体做红队复核；用定时任务卡节点 |

三人都是"半职"：A、B 各自也要跑 DSH（读资料、跑脚本），C 负责把 A、B 的产出接进智能体。**不要设"纯文档人"**——文档是各自的产出自然沉淀，不是第四份工作。

## 4. 主干：第一天就定"数据契约"

三人并行最容易翻车的地方不是能力，是**各写各的字段**。必须在开工第一天由 C 主导、三人签字确认三个 JSON schema：

```json
// content_map.json —— 任务1
{"topic_id":"T01","topic":"代数式与整式运算","objectives":["..."],
 "indicators":[{"indicator_id":"T01I1","desc":"表示数量关系并代入求值",
   "curriculum_ref":{"code":"CR01","pdf_page":62,"text_page":55},
   "textbook_pages":"上册68—109","materials":["Q001","Q002"]}]}

// diagnosis.json —— 任务2
{"student_id":"D01","class_id":"DC01","coverage":{"records":12,"expected":27,"ratio":0.44},
 "by_indicator":[{"indicator_id":"T01I2","observed":3,"score_rate":0.67,
   "evidence":["DR0001","DR0007"]}],
 "flags":["记录不足"],"confidence":"low"}

// recommendation.json —— 任务3
{"target":"D01","problem":"去括号后符号错误","suggestion":"...",
 "materials":["Q015"],"sequence":["回顾同类项","变式1","变式2"],
 "hint_policy":"分步提示，不直接给答案",
 "observe_next":"下次同类题符号正确率","adjust_if":"连续2题仍错则回到去括号专项"}
```

配套统一 ID 规范（全部沿用赛题原始编号，不自造）：主题 T01–T03、指标 T0xIx、材料 Q001–Q054/教材/学习卡、学生 D01–D40、班级 DC01/DC02、节点 N01/N02、作答事件"学生-节点-材料"。

**为什么这一步值一天**：C 的智能体能直接吃 A、B 的产出；B 的统计能被 A 引用；三份材料的口径天然一致；独立评测数据来了以后只换输入不换代码。

## 5. 五阶段 × DSH 动作

### 阶段 0 立项与契约（0.5–1 天）
- 目标：仓库骨架 + 三份 schema + 数据只读副本 + 质检基线。
- DSH 动作：建目录 `data/(只读)`、`src/`、`out/`、`docs/`；把"原始赛题文件只读、异常先出报告"写进项目记忆（target=key），三人共用同一口径。
- 产物：schema ×3、README（怎么跑、跑出什么）、基线统计（40 生 / 806 记录 / 54 题 / 799 唯一作答事件）。
- 验收：任意一人 clone 后一条命令能复现基线数字。

### 阶段 1 内容图谱（任务 1，2–3 天，A 主责）
- DSH 动作：批量读课标 PDF 与 8 份教材切片，抽"课标条目—教材页码—题目"三元组；用子智能体并行做 54 道题的"主题×指标"打标，输出矩阵 + 低置信度清单。
- 关键取舍：**题目打标必须有第二人复核**，尤其是解答题——这是任务 2、3 的地基，错一个指标，后面三个案例全歪。
- 产物：content_map.json、题目-指标矩阵 CSV、内容图谱表（可直接进 PDF 第 4–7 页）。

### 阶段 2 质检 + 诊断（任务 2，3–4 天，B 主责）
- DSH 动作：写 `qc.py` → 输出异常清单；写 `diagnose.py` → 输出个体/群体两层指标；每个结论附 evidence（记录编号列表）。
- 必须显式处理的四类情况（见第 6 节），并在文档里写"处理方式 + 影响"。
- 产物：quality_report.md、diagnosis.json、班级对比表（DC01 vs DC02，同节点同题集）。

### 阶段 3 建议 + 三案例（任务 3，2–3 天，A/B 共担，C 收口）
- 三个案例正好覆盖赛题给的三种类型：**部分得分**（从解答题分点评分定位关键步骤）、**表现较好**（给变式/迁移）、**记录不足**（设计补充练习与观察）。
- 建议必须可执行：材料编号 + 顺序 + 提示方式（不直接给答案）+ 后续观察点 + 调整条件。
- DSH 动作：让子智能体扮演"挑刺评委"，逐条质疑"这条建议的依据是哪条记录"；不通过的退回重写。

### 阶段 4 封装成智能体（1–2 天，C 主责）
- 三层：① 数据层（清洗后的宽表）② 分析层（可复现脚本，输入任意学生集输出 diagnosis.json）③ 交互层（CLI 或简单 Web：选学生/班级 → 出诊断卡 + 建议卡 + 依据跳转）。
- **必须能对未见过的数据跑通**：赛题明确另有 10–20 名学生、100–400 条记录的独立评测集。所以：禁止硬编码学生 ID、禁止按题目编号写死规则、缺失即"未观测"而非"未掌握"。
- 产物：`run.sh`/`run.ps1` 一键出全套 JSON；演示用的固定输入样例。

### 阶段 5 材料与答辩（2 天）
- PDF ≤20 页结构建议：1 封面/摘要 · 2 需求与赛题理解 · 3 智能体总体架构 · 4–7 任务1内容图谱 · 8–11 任务2质检与诊断（含四类数据处理） · 12–15 任务3建议与三案例 · 16 评测集泛化与合规 · 17 创新点 · 18–20 验证与复现说明。
- 视频 5 分钟脚本：0:00–0:30 问题与目标｜0:30–2:00 三项任务跑一遍｜2:00–4:00 三个案例（含"点开依据"这一步）｜4:00–4:40 独立数据泛化｜4:40–5:00 创新与边界。**"依据查看方式"是规则点名要求的镜头，别漏。**
- 答辩 10 分钟：6 分钟结果 + 2 分钟方法可信度 + 2 分钟边界与调整机制。评委最可能问的三个问题：数据缺失怎么算、建议凭什么、换一批学生还行不行。

## 6. 质量闸门：我从数据里实测出的四个坑

1. **重复记录**：806 条记录只有 799 个唯一"作答事件"，7 条是修订版本=2。口径：取最高修订版本为准，旧版本留档用于"修订过程"分析；不能两条都计入总分。
2. **未观测 ≠ 零分**：评分状态 已评分 795 / 待评分 6 / 未作答 5。后 11 条必须单列，计入分母会系统性拉低学生水平，正是赛题点名的"避免将缺少记录直接解释为未掌握"。
3. **两个节点题目集不同**：N01 可用 27 题（T01 + 一元一次方程），N02 可用 45 题（新增方程组、不等式）。**跨节点直接比均分是错的**（N02 满分 696 vs N01 648，且题不同）；班级/学生对比必须锁定"同节点 + 同题集 + 同指标"。
4. **覆盖率极不均衡**：每生记录数 4–28 条。必须先算"该指标被观测次数/应观测次数"，再谈掌握度；覆盖率低的指标只能给"待观察"，不能给"薄弱"。

另：18 道解答题有分点评分（795 条有评分点），268 条有解答过程——这是"部分得分"案例的唯一证据源，务必按评分点拆到步骤，不要只用总分。

## 7. DSH 干不了的事（写进文档的"边界"反而加分）

- 不能替你判断"这个知识点在七年级该讲到什么深度"——教学语义必须人来定。
- 不能保证 LLM 生成文本的合规性——规则第六条要求大模型生成内容做合规校验，需加一道规则/人工复核。
- 不能录屏、不能替你做现场答辩。
- 不要把 DSH 会话里的中间结论直接当结论：所有进材料的数字，必须能由脚本重跑出来。

合规红线：数据仅限本赛题使用、赛后删除、不得引入真实学生个人信息；开源组件与预训练模型须标注来源与版本。

## 8. 三周节奏（按 T-21 天估，拿到正式截止日期后整体平移）

| 周 | A 内容官 | B 数据官 | C 工程与表达 | 周检查点 |
|---|---|---|---|---|
| W1 | 课标/教材结构化，54 题打标 | 质检脚本 + 基线统计 | schema + 仓库 + 数据契约 | 契约评审（三人签字） |
| W2 | 内容图谱定稿，复核打标 | 诊断指标 + 班级对比 | 智能体骨架 + 交互层 | 三案例选题定稿 |
| W3 | 任务3建议文案 | 独立数据泛化测试 | PDF/PPT/视频 + 红队复核 | 全流程彩排 1 次 |

每周一次 30 分钟"红队会"：只做一件事——随机抽 3 个结论，问"依据在哪"。抽不出来就返工。

## 9. 一页速查

- 交付物四件套：PDF≤20 页、成果包（JSON/CSV+字段说明+样例+操作说明）、MP4≤5min、答辩 PPT（10+5 分钟）。
- 分数结构：材料 80% + 答辩 20%；文档与演示质量占一整维度，别把它当附属品。
- 三项任务一条链：内容图谱（要求）→ 诊断（表现）→ 建议（教学），每条建议要能回指"要求 + 表现"。
- 三个案例三种类型：部分得分 / 表现较好 / 记录不足。
- 四类数据问题必须写处理方式：缺失、异常、重复、覆盖不足。
- 一个隐藏考点：独立评测数据（10–20 生、100–400 条）能跑通。

# 附录 A：第一天执行清单（牵头人版）

目标：**一天结束时，任意一名队员在自己电脑上执行一条命令，能复现同一组基线数字，并且三份 JSON 的字段名已经冻结。**

## A1. 启动会 40 分钟（09:00–09:40）

议程固定四段，不展开讨论技术细节：

1. **10 min 讲评分结构**：把 16 个评分项打印贴墙。强调一句："评委只看层 A 的结果和证据，工具用什么都行，但换一批学生要能跑。"
2. **10 min 定"今天不做什么"**（负面清单，比待办更重要）：不写界面、不做建议生成、不选案例学生、不碰 PPT。
3. **10 min 定角色与文件所有权**：谁改哪个目录，写进 README 第一屏。
4. **10 min 定接口骨架**：只过三份 JSON 的顶层字段名和必填项，内容下午再填。

牵头人开场五句话（可直接念）：
> 这个赛题不是比谁模型强，是比谁能把"课标要求—学生表现—教学建议"这条链走通，并且每一步都有据可查。
> 所以我们今天不产出任何结论，只产出"能产出结论的流水线"。
> 三个人从今天起各管一块地，互不越界，靠 JSON 接口对接。
> 今天所有东西的验收标准只有一条：别人能不能一条命令跑出来。
> 今天结束前我们会冻结字段，冻结之后改动要开会。

## A2. 三个当场必须定死的决定

| 编号 | 决定 | 内容 | 反悔成本 |
|---|---|---|---|
| D1 | 范围冻结 | 3 主题（T01/T02/T03）× 54 题 × 40 生 × 2 节点（N01/N02）× 2 班（DC01/DC02）。范围外一律进 backlog，不进本周 | 低（范围小可以扩，范围大收不回来） |

## A7. 第一天绝对不要做的三件事

1. **不要先写界面**。界面会随 schema 返工三次；第一天只写"能吐 JSON 的脚本"。
2. **不要三人共用一个会话/一个文件夹**。一人一个 DSH 工作区，靠 git 同步；共用必然互相覆盖。
3. **不要先挑案例学生**。案例要"有代表性"，代表性来自覆盖率与指标分布——今天先把这两张表做出来，明天再挑人。
